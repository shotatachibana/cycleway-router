# road_network

## 目的

CLAUDE.mdの「専用道路の定義」で採用した(iii)方式(専用道路クラスタ間を一般道で
長さ上限・ペナルティつきで接続)、および「設計上の未決事項」1の追記
(2026-09-20: 一般道路網も含めて全てクライアントサイドに配信し、任意地点間検索を
維持したい)に対応する。関東地方の一般道路網を取得し、経路探索に使える形の
軽量なネットワークデータに絞り込む。

**このタスクではまだ経路探索本体(専用道路への低コスト・一般道への高コスト
ペナルティ付けや、Dijkstra実装)は作らない。** あくまで「クライアントに配信する
一般道路網データをどこまで軽量化できるか」を検証し、現実的なファイルサイズに
収まるかどうかをユーザーに報告するのが目的。収まらない場合は、道路クラスの
絞り込み・ジオメトリ簡略化・対象地域の絞り込み・配信形式(バイナリ化等)を
比較して再度ユーザーに提案する。

## 計算・処理してほしいこと

1. `data/raw/osm_pbf/kanto-latest.osm.pbf`(Geofabrik、約450MB、2026-09-20取得)
   から、`osmium tags-filter`で自転車が走行しうる道路クラスに絞り込む
   - 含める: `primary`, `secondary`, `tertiary`, `unclassified`, `residential`,
     `living_street`, `service`, `track`, `cycleway`,
     `primary_link`/`secondary_link`/`tertiary_link`, `trunk`/`trunk_link`
     (トンネル・自動車専用指定は要除外検討)
   - 除外: `motorway`/`motorway_link`(日本では自転車通行不可)、
     `footway`/`steps`(今回の「一般道接続」の対象外。将来的に
     `bicycle=yes`が明示されたfootwayを含めるかは別途検討)
   - この道路クラスの選定基準は`config.yaml`に外出しし、後で変更して
     比較できるようにする
2. 絞り込んだ後のファイルサイズ(PBF)を確認する
3. 実際にクライアント配信するとしたらどの形式・粒度になるかを試算する:
   - GeoJSON変換後のサイズ
   - 座標の桁数を減らす(小数点以下5桁=約1m精度で十分)・不要タグを削る場合の
     サイズ削減効果
   - Douglas-Peucker等でジオメトリを簡略化した場合のサイズ削減効果と、
     経路の見た目・接続判定への影響
   - (参考)GeoJSON以外のバイナリ形式(例: protobuf、独自のノード・エッジ配列を
     TypedArrayでシリアライズしたもの)にした場合の概算サイズ
4. 上記の結果を一覧にして、「これなら現実的」と言えるサイズに収まっているか、
   収まっていなければ他にどんな軽量化・絞り込みの余地があるかを整理する

## 入力

- `data/raw/osm_pbf/kanto-latest.osm.pbf`(Geofabrik、ODbL、2026-09-20取得。
  `data/datasets.txt`に追記予定)

## 出力

- `data/interim/osm_pbf/kanto_roads_filtered.osm.pbf`: 道路クラス絞り込み後のPBF
  (gitignore対象)
- `results/tables/road_network_size_comparison.csv`: 絞り込み条件・簡略化条件
  ごとのファイルサイズ比較表
- (参考用)`results/figures/`に一般道路網の分布図があれば添付

## 確認してほしいこと

- 絞り込み後の一般道路網が、クライアントサイド配信として現実的なサイズ
  (目安: 圧縮後で数十MB程度に収まるか)に収まりそうか
- 収まらない場合、どの軽量化案(道路クラスをさらに絞る/ジオメトリ簡略化を強める/
  対象地域を絞る/バイナリ形式にする)を採用するかをユーザーと合意する
- この結果をもとに、次のタスク(専用道路+一般道の統合グラフ構築・経路探索
  ロジック)に進む
